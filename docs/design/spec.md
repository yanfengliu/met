# The Met — design spec

The contract every part of this repo builds against. Change it here first, in the same commit as the code that needs the change.

## Product

One page, `index.html`. It shows a procedural model of The Metropolitan Museum of Art's main building on Fifth Avenue, New York, in its present-day form, outside and inside. The model is never simply loaded: it is assembled by an ordered list of build steps, and the viewer plays that build forward or backward, one step at a time or continuously, scrubs it, jumps between chapters, and orbits, zooms and moves freely at any point. The page opens on the finished building, the last frame of the build; Play runs the build from the empty site. A walk mode puts the viewer on the ground in first person, to walk through what is built at the current position.

The order of the build is the order the real building grew: chapters are historical eras (the 1880 Vaux building, the 1902 Hunt facade and Great Hall, the McKim, Mead & White wings, the Roche-Dinkeloo additions, the 2014 plaza). Within a chapter, steps follow the order a builder would raise it: ground and footprint, structure and walls, openings and ornament, interior, roof. Only parts that exist today are modelled; each appears in the era it was built. The research behind the chapter list is in `docs/research/`.

Interior spaces are reached in three ways: interior camera presets, a horizontal section cut that removes everything above a chosen height, and a floor picker that shows one floor at a time with everything over it removed. Ten of them hold placeholders of real objects on view there, sized and coloured from The Met's CC0 collection data (Collection).

## World frame

- 1 unit = 1 metre. +Y is up. +X is Manhattan north (up Fifth Avenue). +Z is Manhattan east (toward Fifth Avenue, so the main facade faces +Z). Right-handed.
- The Manhattan grid is rotated about 29° clockwise from true north. Only the sun direction uses true compass bearings; everything else is in grid axes.
- Origin: Fifth Avenue sidewalk grade, on the axis of the central entrance (the Great Hall's east-west axis), in the plane of the Hunt facade's main wall face behind the column screen.
- The block polygons in `docs/research/exterior.md` section 2 are the walls' outer faces (the OSM outline). On a line two blocks share, the older block builds the wall, inside its own polygon, and the newer builds none there. On the building's outer outline, mouldings (cornices, string courses, sills, copings and their modillions) may project up to 1.5 m beyond the line; walls and glass never do (coordinator, 2026-10-11).
- The decoded floor map (ignored, under `research/cache/`) and every plan position in `docs/research/interior.md` sit 3.1 m +Z of this frame; subtract 3.1 m from their Z (correction of 2026-10-11, recorded in `interior.md`).
- Named levels, extents and key dimensions live in `src/model/frame.ts`, one constant per fact, each with a comment naming its source in `docs/research/`. Builders read them from there and never restate a number another builder depends on.

## Build-step API

Area modules (`src/model/site/`, `core/`, `hunt/`, `mmw/`, `roche-north/`, `roche-south/`) export named step arrays; `src/build/sequence.ts` composes each chapter of `src/build/chapters.ts`, in that order, from those arrays (its `COMPOSITION` table), so a modeller adds steps without touching it. A step's `chapter` must name the chapter its array is composed into (a test checks it); a chapter may have no steps yet. Every step array an area module's `index.ts` exports must be composed (a test checks it). Step ids are unique, stable and kebab-case, because URLs and tests name them. The types live in `src/build/types.ts`.

A step's `year`, when set, lies inside its chapter's `years` (a test checks it; `before 1872` means up to 1872). So Roche's 1970 information desk in the Great Hall is built in `roche-steps-lehman-1975`, and `mckim-mead-white-1926` runs 1904–1956 to hold its two 1956 steps.

```ts
interface StepDef {
  id: string;              // unique, stable, kebab-case
  chapter: ChapterId;      // from src/build/chapters.ts
  title: string;           // at most 48 characters, shown in the timeline
  detail?: string;         // at most 200 characters, shown under the title
  year?: string;           // overrides the chapter's years in the label, e.g. '1975'
  motion: Motion;          // how this step's pieces arrive
  stagger?: Stagger;       // the order pieces arrive in within the step; default 'order'
  weight?: number;         // playback duration multiplier; default 1
  focus?: CameraFocus;     // what the follow camera frames during this step
  build(kit: Kit): void;   // adds this step's pieces
}

interface Kit {
  // One piece: a shared geometry, a shared material and its final world matrix.
  add(geometry: BufferGeometry, material: Material, matrix: Matrix4, order?: number): void;
  // One piece of a door or an artwork: as add, and the timeline keeps its tag (Piece tags below).
  addTagged(geometry: BufferGeometry, material: Material, matrix: Matrix4, tag: PieceTag, order?: number): void;
  // A light that switches on with the step; at most 8 in the whole sequence, never shadow-casting.
  light(light: PointLight | SpotLight): void;
}

interface PieceTag { kind: 'door' | 'artwork'; id: string } // id stable and unique within its kind: a door's own id, an artwork's Met object ID

interface Chapter { id: string; title: string; years: string; summary: string } // src/build/chapters.ts

type CameraFocus =                                         // default { kind: 'pieces' }
  | { kind: 'pieces' }                                     // this step's piece bounds, from the current viewing direction
  | { kind: 'box'; min: Vec3; max: Vec3 }                  // this world box, from the current viewing direction
  | { kind: 'view'; position: Vec3; target: Vec3 }         // this exact camera
  | { kind: 'preset'; id: string };                        // a preset of src/viewer/presets.ts

type Motion =
  | { kind: 'rise'; distance?: number }                    // slides up from below its final place
  | { kind: 'drop'; distance?: number }                    // slides down from above
  | { kind: 'grow' }                                       // scales up in Y from its own base
  | { kind: 'pop' }                                        // scales up from its own centre
  | { kind: 'slide'; from: readonly [number, number, number] }; // arrives from this world offset

type Stagger = 'order' | 'x' | '-x' | 'z' | '-z' | 'y' | 'radial' | 'none';

type Vec3 = readonly [number, number, number];
```

- **Batching.** Within one step, pieces that share the same geometry object and the same material object become one `InstancedMesh`. Steps never share a mesh, so each step shows and hides independently. Builders therefore create one geometry per distinct shape and reuse it, and take materials from the shared palette (`src/model/palette.ts`) or their own module, never cloning a material per piece.
- **Piece tags** (contract C1 of work unit 2). `addTagged` adds a piece of a door or an artwork. The timeline keeps each tag with the instance the piece lands in: `Timeline.tagOf(mesh, instance)` gives it (null for an untagged piece), and `BuiltStep.tags` lists them per mesh. A door's pieces batch only with pieces of the same door, so each door has meshes of its own and can be shown or hidden on its own; an artwork's pieces batch as untagged pieces do. Tags are not timeline state: they never change with `t`, and every piece's matrices, colours and arrival are what `add` would give it. A tag of another kind or without an id fails, naming the step and the piece (`src/build/tags.test.ts`).
- **Composite pieces.** A part made of several materials (a window: frame and glass) is several `add` calls with the same `order`; pieces with equal stagger keys arrive together, and a test checks that every role of a window or door part arrives with the others. Spatial staggers key on the piece's world bounding-box centre, rounded to 1 cm; `radial` keys on the horizontal distance from the centre of the step's bounds; `order` defaults to the call's index within the step.
- **Motion details.** `rise` and `drop` travel `distance` metres, by default the piece's own height but at least 3 m; `grow` scales world Y about the bottom of the piece's world box; `pop` scales about its centre with a slight overshoot. Windows are paced by rank: of R distinct keys, rank r starts at `r / (R − 1) × (1 − d)` and lasts `d = max(0.25, 1 / R)`.
- **Materials.** A material with `userData.castShadow === false`, or any transparent one, never casts shadows (glass, water, the flat ground materials of the palette and the bronze of the entrance doors' leaves, Page, Doors). A material with `userData.solid === false` is walked through: the walk mode's collision leaves its pieces out (water, foliage, the jets of the plaza fountains, and the passable copies of the bronze and dark glass of the entrance doors' frames, the bronze beside them and their transom lights; Page, Doors: Walking); every other material is solid, the doors' leaves among them, which collide where the door layer stands them, apart from the static world (Doors: Walking). The engine gives every model material the section-cut clipping plane, except one with `userData.sectionCut === false`: the cut leaves it whole and its cap pass leaves its meshes out. Everything the site builds as landscape opts out (trees, ground, streets, paths, rocks, walls, fences, lamps, benches, fountains and the plaza's furniture), using the site's own copies of materials the building shares, so only the building is cut; the excavation, the pad and the 1970 front steps are the building's and stay cut. A floor view hides the landscape that rises above its cut whole instead (Page, Floor picker). Builders never set `clippingPlanes`.
- **Solids and sheets.** A piece the walk collides with or the cut would cap is a solid or a sheet. A solid is closed along vertical lines: every vertical line crosses it an even number of times, and its inside lies between its first and second crossings, its third and fourth, and so on. Each upright face of a solid has the solid's inside behind it, so a part with sides has a top and a bottom too. The one exception is a two-sided membrane, two faces back to back, which has no inside to lose (a channel's end against a reveal, `src/model/lib/wall.ts`). A solid's faces look out: each closed part holds its inside behind its faces, and no surface folds through itself into a pocket whose faces look in. No piece's matrix mirrors it, since an instanced mesh would draw such a piece with every face turned in; a part is mirrored in its geometry, which `MeshBuilder.transform` turns back. A sheet is a surface with no inside, such as a glass pane, paving laid on the ground, the terrain or a surface standing upright, which no vertical line crosses. Its builder declares it with `sheet` (`src/model/lib/sheet.ts`), on the geometry, so a cached part is a sheet wherever it is placed. The walk stands on a sheet but reads no inside in it, whatever its crossings. The cut's cap pass leaves sheets out (`capsMesh`, `src/viewer/section-cut.ts`). Parts of one solid may overlap, and the walk reads an overlap as outside (Walk mode: When the build moves), so no vertical line runs through overlapping parts for as long as settle's span, 1.749 m. `src/model/closure.test.ts` checks every piece at t = N. Each solid is closed by its own edges and has a face that does not stand upright. Along lines through up to 24 of its faces, the walk's crossing query reads it closed, as many of its faces look up as down, and no overlap is that long in any of its walked pieces. Each closed part's volume, read through its faces and signed by its piece's matrix, is positive. No line through its faces, nor any of a grid of 64 lines a side over it or two beside each of its open edges, crosses a stretch where more of them look down than up, though a pocket narrower than a grid cell that no open edge borders can be missed, as can lined-up open ends that wind to an inside between them. Each upright face has more inside behind it than in front, or the same on both sides within an overlap. No piece of the model is mirrored. The sheets are counted by step and material.
- **Lights.** A step light's intensity follows its step's progress (0 at `f = 0`, its own intensity at `f = 1`); lights never toggle visibility, so shaders never recompile during playback.
- **Timeline position.** With N steps, the position `t` runs over `[0, N]`. Step `i` (0-based) has local progress `f = clamp(t − i, 0, 1)`. At `f = 0` none of its pieces is visible; at `f = 1` every piece sits exactly at its final matrix; in between, each piece moves through its own window of `f` according to `motion` and `stagger`, and an arriving piece is briefly tinted so the eye finds it. An integer `t = k` is a rest position: steps 1..k (1-based) are complete and nothing is moving.
- **Determinism.** The scene state at `t` is a pure function of `t`. Evaluating `t` after any history of plays, reversals, steps and scrubs gives byte-identical instance matrices, colours and visibilities to evaluating it fresh. Caching may skip rewriting unchanged values; it may never make the result depend on the path. This is what makes backward playback exact, and a test asserts it.
- **Playback.** Play forward and play backward run `t` continuously at `weight × BASE_SECONDS / speed` seconds per step and stop at 0 or N. Step forward animates to the next integer, step back to the previous one; a second press while moving retargets. Scrubbing sets `t` directly. Speed is 0.5×, 1×, 2× or 4×. Play forward at N starts again from 0, and play backward at 0 from N. The player is pure logic with no DOM and is unit-tested on its own.

## Page

- **Timeline bar** (bottom): buttons for start, step back, play backward, play/pause, step forward, end; a speed control; the Walk toggle (`walk-toggle`, pressed in walk mode); a scrubber over `[0, N]` with chapter boundaries marked; a label `Step k / N · <year> · <chapter> — <title>` with the step's detail beneath, where k = ⌈t⌉ (the step just completed at a rest position, the step playing in between) and k = 0 reads `— Empty site`. Every control has an accessible name and a `data-testid`. While walking the bar folds into a strip at the bottom right holding the Timeline button (`bar-toggle`, "Show the timeline", with `aria-expanded`) and the Walk toggle; the Timeline button unfolds the whole bar, whose controls then work as in the orbit view, and folds it again; each entry into walk mode starts folded. In the orbit view the bar is always whole and the Timeline button is hidden.
- **Chapter menu**: the chapters in order, with their years and summary; choosing one moves to the start of its first step; a chapter with no steps is shown disabled.
- **View menu**: exterior and interior camera presets (named in `src/viewer/presets.ts`: `fit` presets frame the model's bounds from a direction; `look` presets are explicit cameras with an optional `fov` and, for straight-down views, `up`), a follow-camera toggle that frames each step's `focus` during playback and switches off when the user drags, zooms or moves the camera by keys (a press without movement leaves it on), one button per walk spawn (`walk-spawn-<id>`, "Walk from ...", which enters walk mode there), and a section cut (an on/off toggle and a height slider). The cut keeps `y < cut` for every building material, shadows included (landscape opts out; see Materials), and draws the back faces of cut solids in one flat colour so cut walls read as solid from above. Every solid is closed along vertical lines, with an inside behind each upright face, so its cut, seen straight down, never shows what lies under it. The pass leaves out the sheets, surfaces with no inside (Build-step API: Solids and sheets). A part wound inside out shows its lit inner faces where the cut opens it, not the cut colour. A two-sided membrane in a piece the cut passes through shows the cut colour from either side. That pass draws only the pieces the cut passes through, by their current bounds (`src/viewer/cap-pass.ts`), so a piece under the cut never shows the cut colour, and it is drawn 4 depth-buffer steps nearer (`CAP_DEPTH_BIAS`, `src/viewer/section-cut.ts`), so a cut solid's face that lies on another piece's face (a stair's underside on its floor, a flight's end on its landing) shows the cut colour instead of z-fighting with it.
- **Floor picker** (`floor-picker`, a group named "Floor"): a column of buttons at the left of the view, All (`floor-all`) at the top and the floors under it from the highest down (`floor-<id>`), the choice in view pressed; Page Up and Page Down move up and down it. The floors are data in `src/viewer/floors.ts`, each with its id, label, level (from `src/model/frame.ts`), the section-cut height that shows it and the plan area the camera frames, picked by looking at the model:
  - `ground` (`GROUND_FLOOR_Y`), cut at 3.1 m: under the Temple of Dendur pool's slab (underside 3.41 m), the lowest slab over the ground floor.
  - `main` (`MAIN_FLOOR_Y`), cut at 7.8 m: under the Wallace Wing's mezzanine (underside 7.91 m), the lowest slab over the main floor, so no mezzanine (8.4 to 10.0 m) covers it.
  - `second` (`SECOND_FLOOR_Y`), cut at 12.7 m: over the Roche wings' second floor (12.34 m) and under the Fifth Avenue links' second-floor slab (13.15 m); every cut from 13.15 to 15.0 m slices a slab or roof, and one at 15.2 m leaves the Morgan wing's roof over its second floor.
  - `roof-garden` (`ROOF_GARDEN_Y`), cut at 27.4 m and framing the garden alone: over its potted trees (26.9 m) and the park's tallest crown (27.3 m); nothing stands over it.
  - Choosing a floor sets the cut to the floor's height, hides the landscape that rises above it, and frames the floor's storey from above at 65°, from the side the camera looked from (the orbit's horizontal direction is kept), turning the follow camera off as a preset does; the framing is fitted again after a resize while the camera stands there. Choosing it again frames it again.
  - Hidden landscape (`src/viewer/floor-view.ts`): every landscape mesh whose highest standing piece rises above the cut, whole, never sliced; a landscape piece at least 30 m across both ways is ground (the terrain, the merged park paths) and never hides, and pieces of one step with the same final matrix (a tree's trunk and crown, a lamp's post and globe) hide together. Hidden meshes neither draw nor cast shadows, and the zoom's pick passes through them.
  - All gives back the cut the user had before the first floor was chosen, on or off at its height, shows every landscape piece again and leaves the camera where it is. Moving the cut slider or pressing the cut toggle ends the floor view instead (All is pressed again) and the hand-set cut stands as the user's own.
  - Walk mode belongs to the walker: entering it ends the floor view as All does, the picker hides while walking and the floor keys do nothing. The walk's collision never reads the floor view, so it is the same whether a floor was chosen or not.
  - Like the cut, the floor view is a view filter: it sets the cut and each hidden mesh's layer mask, never what the timeline writes, and which meshes hide depends on the floor alone, read from each piece's final matrix, so the scene at `t` stays a pure function of `t` (and the floor).
  - Known limits: the map's floor-3 plates (the north end pavilion's at 15.9 m, the 1924 American Wing's at 13.9 m) have no entry, because no single cut shows them without slicing roofs elsewhere; the mezzanines (map floor 1M) have none, and the main floor's cut passes under them; where a wing's second floor lies higher than the frame's level (the Fifth Avenue links' at 13.6 m, the American Wing's at 14.1 m), the second floor's cut shows that wing's floor below. Landscape hides by whole meshes, so one standing piece over the cut hides every piece of its mesh, and an object placed with different matrices (the magnolias by the steps) can lose its crown alone.
- **Camera framing**: presets and the follow camera frame the part of the canvas above the timeline bar; walking, the view is the whole canvas (Walk mode: The screen). A preset lands exactly where it says, even right after a drag. When the canvas changes shape, the preset in view is fitted again, as long as the camera still stands where the preset put it. The neutral workspace ground, not part of the model, lies 0.5 m below the lower of grade and the model's lowest point, so model terrain always lies on top of it.
- **Follow camera at load**: on unless the query sets `shot=1`, a `view=` that names a preset, `cam=`, `walk=1` or a `floor=` that names a floor. It moves the camera only while the build plays.
- **No WebGL 2**: if the renderer cannot start, the page says WebGL 2 is not available, gives the browser's reason and what to do, and does not report a build failure.
- **Camera** (orbit view): drag to orbit, right-drag to pan, and the wheel, a pinch or a middle-button drag to zoom toward the pointer (`src/viewer/zoom.ts`). A zoom step moves the camera along the ray under the pointer and keeps its view direction. In, it moves a tenth of the distance to the surface under the pointer (`src/viewer/pick.ts`: the first drawn piece, or the workspace ground; above the section cut, cut pieces are passed through, and so is the landscape a floor view hides), at least 0.25 m, and stops 0.5 m before that surface, or sooner on the ray where the ray comes down to the camera floor (0.4 m above the workspace ground), which it then heads for instead; over open sky it flies on as if a surface stood 10 m ahead. Out, it moves a tenth of the distance to the orbit target, at least 0.25 m, until the target is 6 km away, or, backing down a ray that points up, until the camera stands on the camera floor, still on the ray. Where the camera is at both bounds at once (zoomed out to 6 km, then lowered onto the floor by Q), a notch out first brings the target onto the view axis at the near bound's depth and then moves (`zoomStep`). Each step puts the orbit target on the view axis at the depth of what it heads for. Steps never shrink toward an invisible point, so every notch moves the camera until one of the two bounds, and either bound gives way at once to the other direction (`docs/learning/defect-register.md`, "The wheel stops zooming"). The camera stays 0.4 m above the workspace ground: a pan or an orbit that takes it lower is undone by lifting the camera and its target together, so the view does not turn. That lift is the last move before each frame renders, so no frame renders from under the floor; what the drag still owes carries the camera on over the next frames, each lifted again. A zoom first spends what a drag still owes and makes that lift, then takes its ray. A press on the canvas is followed to its end wherever its events land, as they may once its pointer capture is lost: the zoom hears a press's moves, release and cancel on the document, and the rig sends a cancel that lands on another element on to the canvas, not bubbling, for the orbit controls, which hear a cancel only there (review 11, F37). A middle-button drag ends when that button is let go, even while another stays down. One kind of input holds the camera at a time, the fingers on the screen, any number, or one mouse or pen (`src/viewer/pointer-arbiter.ts`; work unit 10). A press on the canvas in the orbit view takes the camera when nothing holds it, and a finger joins fingers that hold it. Every other press is refused: a pointer of another type, a second mouse or pen, and every press while walking. The orbit controls and the zoom each hear a pointer that holds the camera from its press to its end, its release or cancel, wherever its events land, and nothing of any other pointer: not a refused one, not one pressed elsewhere on the page, not a hover. A pointer keeps the camera through a change of mode until its end, and a refused one stays refused until its end, even once the camera is free. The camera is free once both have heard each holder's end, so neither ever holds two kinds of input. The orbit controls keep a finger's position but not a mouse's or a pen's, and took every pointer they heard for their own: a mouse and a finger down together threw inside them, as did a mouse and a pen, a middle button pressed while a finger turned the view and a finger lifted elsewhere during a mouse drag, and a pen hovering during a mouse drag turned the view (work unit 2, review 11, F39).
- **Keyboard**, by physical key (`event.code`), in two modes. A key takes the meaning of the mode in force when it is pressed, so a key pressed right after F, before the next frame, already belongs to the new mode. A focused button keeps Space and Enter, a focused slider other than the scrubber keeps its arrows, Home, End, Page Up and Page Down, and a text field keeps every key.

  | Space | play/pause | jump |

  Orbit-view moves run at half the camera-to-target distance per second, at least 1.5 m/s (`src/viewer/orbit-keys.ts`), so they cover the same share of the view from an aerial preset as from inside a hall. They keep the camera above its floor and turn the follow camera off, as a drag does.
- **Walk mode** (`src/walk/`), entered by the Walk toggle, F, a view-menu spawn or `walk=1`:
  - **Body.** A capsule of radius 0.35 m and height 1.75 m, the eye 1.6 m above its feet. It walks at 2 m/s and runs at 5 m/s, jumps 0.45 m and falls under gravity (9.81 m/s²). The walk is a brisk walk indoors, about 1.4 times a person's comfortable 1.4 m/s, because motion seen on a screen looks slower than the same walk in life; 3 m/s read as a jog (work unit 2 audit). The run is 2.5 times the walk, to cross the 300 m building in about a minute; 6 m/s was a sprint.
  - **Ground.** It steps up and down edges of up to 0.35 m, so stairs and the front steps are climbed by walking. It steps up only where its raised body meets nothing overhead: under a ceiling, soffit or lintel too low for it, a step stops it like a wall, so its head never enters what is over it. It walks on slopes up to 40°; a steeper one stops it like a wall, and it slides down one it lands on, the keys unable to push it uphill. It stands on the surface under its centre or, over a gap, on the lower rim of two opposite probes 0.3 m out, so it bridges a gap narrower than about 0.6 m yet falls off an edge as soon as its centre passes it. It slides along walls. Physics runs in fixed steps of 1/120 s, so a walk is the same at any frame rate. The eye eases out of each snap up or down a stair over about 0.1 s, and each frame's eye is interpolated between the eased eyes of the last two steps, so on a flight it never drops while climbing and never rises while descending, no frame moves it more than the climb covers in that frame plus half a riser, and it stays within 0.3 m of 1.6 m over the feet (`src/walk/stairs.test.ts`, `tests/e2e/stairs.spec.ts`).
  - **Looking.** A click on the view asks for pointer lock, and the mouse then turns the view; Esc frees the pointer, as browsers do. A drag with the mouse or a finger turns the view too, locked or not. Pitch stays within ±85°; the field of view is 60°. Choices (work unit 2, M1), each in `src/walk/walk-mode.ts`:
    - A drag turns the view the way the pointer moves, right for right and up for up, as the locked mouse does, so one hand motion means one thing in walk mode whether the pointer is locked or not, as in first-person games on a desk or a phone. The orbit drag turns the other way because it turns the model about a target in the hand, not the head.
    - `LOOK_PER_PIXEL` 0.0013 rad (0.075°) a pixel, locked or dragging: a drag across the view turns it by about its own width (91.5° over 1280 px at 1280×720, 29.8° over 390 px at 390×844), precise enough to look round a gallery; 0.0022 turned 1.8 times that.
    - `CLICK_SLOP` 5 px: a press that travels less before it is released is a click, which asks for pointer lock; more is a drag, which looks. A still click travels 0 to 2 px, and under 5 px a drag would have turned the view by under 0.4°, which nobody means as a look.
  - **The screen.** While walking: the view, now the whole canvas (the projection is centred on it whether the bar is folded or not, so unfolding it never moves the view); a crosshair (`crosshair`) at its centre, on the eye's ray, gold while the look target is a door or an artwork; the Chapters and View buttons at the top right; and the folded bar's Timeline button and Walk toggle at the bottom right. The rest of the bar and the floor picker are hidden. The status line (`walk-status`) says "Preparing walk mode…" for the first frame, then how to look, move and leave until the visitor first walks or looks, at most `HINT_SECONDS` (6 s), and again when the pointer is freed; while the pointer is locked the browser says how to free it. Hidden controls come back by the Timeline button. Walk mode ends by F, the Walk toggle, or a camera preset from the View menu.
  - **Look target** (contract C2 of work unit 2; `src/walk/look.ts`), the only way doors and labels find what the visitor looks at. The hit query (`ModelPicker.hit`, `src/viewer/pick.ts`) casts a ray through the drawn pieces as the zoom's pick does and returns the nearest piece a query accepts, with its mesh, instance, distance and tag; a surface the query does not accept stops the ray, except that a query may pass through untagged transparent pieces (glass, water), so an artwork in a vitrine is found through its glass but never through a wall; a tagged piece the query does not accept stops the ray as a wall does, so a glass door out of reach hides what is behind it (accepting a target and passing through are apart; the zoom's own `distance` still stops at glass). The walking eye asks for the nearest tagged piece within its kind's reach, a door within 2 m and an artwork within 6 m, through transparent pieces. A door's leaves keep 4 mm off their frame and a pair's meet 8 mm apart, so one ray can pass between them: each closed door's doorway, a box over its leaves and those gaps that no camera draws (Doors: The layer), is the door's in the hit query, which the zoom's pick does not read, so the eye meets a closed door anywhere in its doorway (work unit 2, review 17, F46: from the plaza spawn W alone took the crosshair along the middle door's meeting line, where it met nothing, and E did nothing). Walls in front still hide a doorway as they hide the leaves, and an artwork is still found only on the eye's one ray, through untagged glass. Walk mode runs it every walking frame and again whenever the target is read (`WalkMode.target()`, `window.__met.walk.target`), so an action sees the view as it stands then; a read of the facts writes nothing, so the last frame's target, which the crosshair, the prompt and the card show, stands until the next frame (review 17, F45); the same query serves a pointer ray from an orbit-view click. Viewer-side stand-ins, a door's moving leaves for one, join the picker with their own tags through `ModelPicker.register(meshes, tagOf)`, or the hit query alone with `{ zoom: false }`, and leave through `unregister(meshes)`: the queries they join meet them as drawn pieces (visible, on a layer the camera draws, their first `count` instances at instance matrices in world space, the mesh itself untransformed, its bounding sphere trusted as the renderer's culling trusts it, so a stand-in that moves keeps it current), their BVHs are built in the shared cache as they join, and an original moved onto a layer the camera does not draw drops out. `WalkMode.onLookTarget(listener)`, which returns the call that stops it, is the one hook that hears the target: it calls the listener with the target, or null, each time its kind or id changes as walking frames find it (not when only its distance changes, and not on a fresh read, which the next frame tells), and with null when walk mode is left or entered again while a target was seen. Doors and labels both subscribe there; neither adds a hook of its own, nor door or label logic to the picker or walk mode.

Each time the collision is built, while walking or on entering, the walker's place is checked against it (`settle`, `src/walk/walker.ts`); the doors' leaves are no part of this check, and after it a door whose leaves stand in the walker is put clear of it (Doors: Lifecycle). It is buried when the model lies over it with nothing but the workspace ground under it, and embedded when the vertical line through it, from just over its feet to its head, runs inside a piece that arrived since its place was last checked. Along that line a piece's inside lies between its first and second crossings, its third and fourth, and so on. A piece the line crosses an odd number of times is open there and has no inside, and a sheet has none, whatever its crossings. Hits at one height that lie on edges of their triangles and face the same way count once, as where the line passes through an edge or a corner that triangles of one surface share (`crossings`, `src/walk/collision.ts`). Every other hit counts on its own, so two faces back to back, as one part's top under the bottom of the part on it, are two crossings. A line exactly along edges that faces of two overlapping parts in one plane both have reads them once there, a bound. Every solid is closed along vertical lines, with an inside behind each upright face, and a sheet has no inside (Build-step API: Solids and sheets). So a walker that a solid is built through is found, unless it stands on such a line, and a sheet never holds one inside. ## Query contract

`src/viewer/query.ts` is the only reader of the page URL.

| Parameter | Effect |
|---|---|
| `shot=1` | Capture mode: no autoplay, no follow camera, no animation; `window.__shotReady = true` once at least 5 frames have rendered at the requested state |
| `t=<number>` | Timeline position in `[0, N]` |
| `step=<id or 1-based index>` | Position at the end of that step; wins over `t` |
| `view=<preset id>` | Camera preset; one that names no preset is ignored with a warning, as if absent |
| `cam=px,py,pz,tx,ty,tz` | Explicit camera position and target, for sweeps |
| `cut=<metres>` | Section-cut height |
| `solo=<chapter id>` | Build only that chapter (plus `site`), for fast isolated checks |
| `autoplay=1` or `autoplay=0` | `1`: play the build on load, from `t = 0` unless `t` or `step` sets a position. `0`: do not play, the default |
| `walk=1` | Start in walk mode |
| `spawn=<id>` | With `walk=1`, the walk spawn to start at (`plaza`, `great-hall`, `second-floor`); one that names no spawn starts at `plaza` with a warning; without `walk=1` it is ignored with a warning |
| `floor=<id>` | Start on that floor of the floor picker (`ground`, `main`, `second`, `roof-garden`; `all` shows every floor), framed unless `view=` or `cam=` names a camera; one that names no floor, or any with `walk=1`, is ignored with a warning |
| `doors=open` or `doors=closed` | The state every unlocked door takes when its step completes (Doors), at load and after the step was taken away; with `shot=1` the doors stand at it from the first frame, set before the walker is placed. Any other value is ignored with a warning; a locked door stays shut either way |
| `noui=1` | Hide the page chrome |

The renderer keeps `preserveDrawingBuffer: true`, or headless capture reads a blank canvas. `window.__met` exposes read-only facts for tests (step ids, titles, each step's `focus` and piece `bounds`, chapters with their first step and count, presets, bounds, `N`, current `t`, mode, speed, follow, the follow camera's current goal, cut, `floors` (each floor's id, label, name, level and cut), `floor` (the floor picker's choice in view, the landscape meshes it hides and the user's own cut it gives back), view, the camera with its `fov` and the `aspect` of the canvas above the bar, budget stats, `perf.buildMs` (the timeline build alone) / `perf.readyMs` (navigation start to ready) from `performance` marks, `perf.lastDrawn` (the last drawn frame's number, the camera position it was rendered from and its doors as the meshes drew them, Doors: Facts, copied right after the render), and `walk`: the mode (`orbit` or `walk`), whether it is preparing, the spawn last used and the spawn ids, the eye and the unit look direction (null in the orbit view), the on-ground flag, whether the pointer is locked, `bvhMs` (milliseconds of the last collision build), what that build holds (complete steps, instances, triangles) `frameMs` (the median work per walking frame over the last 120, the look target included) and `target` (the look target found afresh when read, writing nothing: the tagged piece's kind, id and distance, or null); types in `src/viewer/facts.ts` and `src/walk/walk-mode.ts`). In capture mode with `walk=1`, the collision is built and the walker placed before the first frame. Every value is a detached, deeply frozen snapshot, so no write to it reaches the page; tests drive the page through its real controls, never by writing state.

`window.__met.label` is the artwork whose card the last frame showed (Collection: Labels): its Met object ID and title, or null.

## Parts library

`src/model/lib/` exports pure functions that return `BufferGeometry` in local coordinates: origin at the part's base centre unless its header says otherwise, +Y up, the part's front facing +Z. Each function's header states its parameters' units and its origin. The set covers what the building repeats: classical column and pilaster (base, shaft, Corinthian capital), entablature and cornice profiles swept along a path, round-arched and flat openings in a wall, windows (frame, mullions, glass as separate geometries), balustrade runs, stairs, domes and saucer domes with or without an oculus, coffered vaults, skylights (ridge and pyramid), glass curtain walls, trees, fountains. Geometry is cached per parameter set so equal calls return the same object, which is what lets the kit instance it. Every part placed as a solid is closed along vertical lines, with an inside behind each upright face, and the glass of the glazing parts, windows and doors is a sheet (Build-step API: Solids and sheets).

A door (`doorUnit`) returns its leaves closed, as one geometry for a build to place (with the leaves' glass as another for a glazed door), and each leaf apart, closed, in the unit's frame, with its hinge (the hinge-side edge's point on the leaf's back face and on its front face, and a unit axis turned so that a positive turn swings the leaf toward the unit's back, −Z; it turns about the back face's point opening toward the back and the front face's opening toward the front) and its swing (which way it may open and how far); `doorLeavesOf` finds the leaves from the closed geometry, for the door layer (Page, Doors).

Placeholders of real objects on view (AGENTS.md non-goals; research, rules and regeneration in `docs/research/collection.md`):
- **Catalogue.** `src/model/collection/catalogue.ts` is generated by `scripts/met-catalogue.ts`, run by hand (`npm run met-catalogue`), never in CI or the build: from the picks (`src/model/collection/picks.ts`: 5 to 12 objects in each of at least 8 spaces), it fetches The Met's Collection API records at one request a second through an ignored cache (`research/cache/met-api/`), stops on HTTP 403 or 429 saying when to retry, rejects a record whose `GalleryNumber` is not its space's unless its pick overrides it, samples colours only from public-domain images (decoded in the system Chrome), and writes the file all at once or not at all. Each entry is one CC0 record: its metadata, the placeholder's derived kind, display, size and colours, where each came from, and its provenance (API URL, fetch date, hashes of the record and image, the sampler's version).
- **The page never fetches.** The catalogue is in the bundle; the page asks nothing of any host but its own and nothing of `research/` (`tests/e2e/network.spec.ts`). No image is a texture or committed.
- **Placeholders.** Each object takes a procedural form at its real size (`src/model/collection/kinds.ts`: a standing figure, a group, a recumbent figure, a bust, a jar or dish, a slab, a block, a canvas, each filling a unit box its piece's matrix scales): kinds figure, bust, vessel, slab, frame and plinth, shown on a plinth, in a vitrine (objects under 0.6 m), on a wall (paintings, and slabs from 0.6 m) or on the floor (`src/model/collection/place.ts`). Paintings show an 8 × 8 grid of their image's colours, blended bilinearly between cell centres (a soft blur, not a mosaic), everything else its sampled mean.
- **One step per space**, after that space's fit-out step, in its chapter and year, composed into an area module's array (`src/model/collection/spaces-a.ts`, `spaces-b.ts`). It pops its artworks in one after another (stagger `order`, one order per artwork, so an artwork's object and its plinth, vitrine or frame arrive together) and frames the space's preset.
- **Colour per instance without a mesh each.** A step's artworks share one material whose shader finds an instance's artwork by the plan position of its matrix in a float table (`src/model/collection/material.ts`): colour, roughness, metalness and a painting's grid. This holds because every form is centred in X and Z and the steps pop their pieces, which never moves them in plan, and because a step's artworks stand at least 5 cm apart in plan. The timeline's arrival tint still multiplies the colour; the determinism contract is untouched, the table being fixed per step.
- **Placement** (`src/model/collection/placement.test.ts`, at `t = N` against the model without the collection, reading each piece from the instance its step's mesh draws, bound exactly to the piece its step gave `kit.addTagged` and to the one its placement gives): every artwork's pieces stand on the floor their placement names (within 12 mm) or hang against a wall (within 4 cm), no other solid passes through them, and they keep 1 m clear of routes R1–R7 (R5 into gallery 600, R6 into the Engelhard Court, R7 into the Petrie Court) beyond the walker's radius, of the doorway into 600 with its passage's sides, of the Dendur gate's threshold and the rail before it, of the Dendur pool, of the Weston door's passage, of the passages into the Engelhard Court and the Petrie Court's wing and 6 m either side of their wall beyond the walker's radius, and of the swing of the doors that open (the Hunt central arch's and the Weston door).
- **Labels** (work unit 2, M3b; `src/ui/art-card.ts`, `src/viewer/art-label.ts`, `src/viewer/click.ts`). Every piece of an artwork, its plinth, vitrine base and glass and frame included, is added through `kit.addTagged` with the tag `{ kind: 'artwork', id: <its Met object ID> }`, so the look target and a click find the artwork whichever of its pieces they meet. Artwork tags split no mesh: tagged or not, the collection's steps make the same meshes, triangles and scene (`src/model/collection/artwork-tags.test.ts`). One card shows at a time.
  - **Content**, from the artwork's catalogue entry: its title; its maker, the artist or the culture as the record gives it, beside its date (a record that names neither, as the Dendur hall's five Egyptian objects, shows the date alone); its medium and gallery number; its size, height by width by depth in centimetres to the millimetre, naming as estimated the axes the record does not measure (the catalogue's `sizeFrom` `estimate` or `pick`); a plain link, "View on metmuseum.org", to its page there; and the credit "Object data: The Met Open Access, CC0". A record's text shows as plain text on one line: the markup and line breaks a few titles carry from the API (`<i>Rennzeug</i>`) go, their words kept, and nothing of a record is ever parsed as HTML. The link opens a new tab (`target="_blank"`, `rel="noopener noreferrer"`), and the page gives no prefetch, preload or preconnect hint, so nothing fetches it before it is clicked; the page itself asks nothing of metmuseum.org.
  - **Walking**, the card is the look target's artwork, as walk mode's look-target hook (`WalkMode.onLookTarget`) tells each change: it shows while the eye looks at an artwork within 6 m and hides as soon as it looks at anything else. Choice (M3b): the link is reached by freeing the pointer. Esc frees it, as the browser does; the free pointer turns nothing without a drag, so the view and the look target stand still and the card stays for the artwork in view; a click on the link opens the page in a new tab, and the walk goes on. While the pointer is locked the card says "Esc frees the pointer to open the link." Reason: a locked pointer cannot click a link, and Esc is the key the browser already names for freeing it; a key of its own that opened the page would be one more control, and a tab opened by a key in mid-walk would take the visitor out of the walk unasked. A touch screen has no lock, and the link is tapped.
  - **Orbit view**, the card is the artwork a click meets: a press and release within `CLICK_SLOP` (5 px) of travel, summed over its moves as walk mode sums it; a drag never counts, nor a press another finger joins. The click's ray, from the camera through the pointer, runs the hit query (`ModelPicker.hit`) with an artwork-only query (`ARTWORK_QUERY`): the nearest artwork piece at any distance, through glass and water that are no artwork's; any other surface stops the ray, so no artwork is labelled through a wall or a door. A click on anything else, Esc or a camera preset hides the card. So does any change that leaves the camera drawing none of the artwork's pieces, as the picker counts a drawn piece: the build taking it away (Home, the scrubber, playing back past its step); the section cut, by its slider or toggle or a floor view's, lying under every piece; or its meshes on no layer the camera draws. A cut through any piece of it keeps the card, since the picker still meets the artwork there. Entering or leaving walk mode hides it.
  - **A click moves nothing**: the camera, the follow camera and the preset in view stay as they were. Choice (review 6, F25): until a press has travelled `CLICK_SLOP`, its moves are held from the orbit controls and the zoom in the document's capture phase (`src/viewer/click.ts`), only the latest kept. Reason: held moves keep the camera still from the first frame. Restoring the camera after a click would draw a moved frame first, and would have to give back the follow camera and the preset that the move turned off. The gate is a small state machine (review 10, F36). A release below the slop in the orbit view is a click, and its held move is dropped; released while walking, a press is no click, and its held move goes on as a drag's does (work unit 10). The slop passed, another pointer landing, a change of the pointer's buttons (a chord arrives as a move with new `buttons`; review 11, F38) or the loss of its capture sends the held move on once, before the event that ended the hold reaches anyone: a drag turns as far as before, and a pinch's zoom and two-finger pan start from where the fingers are (review 7, F29). From then on every event goes on and nothing is held, until no pointer is down; a pointer landing then is never a click. A cancelled press drops its held move. A lost capture ends no pointer (Pointer Events 3): the pointer stays down, so no other press is a click, until its own release or cancel, which the gate hears on the document wherever it lands (review 11, F37).
  - **Place**: at the bottom left above the timeline bar, whole or folded: walking, above the folded strip at 1280×720 and across the whole width at 390×844; in the orbit view, right of the floor picker. Walking, where the card could reach the middle of the view (at most 1000 px wide), it keeps under the crosshair and, with the bar folded, under the door prompt's place: the band from the crosshair down to 80 px under the centre. With the whole bar unfolded on a narrow screen it keeps clear of the crosshair only, and may reach into the prompt's band, and it scrolls if its text needs more room. That exception rests on the card and the prompt never showing at once: both follow the one look target, the card an artwork's and the prompt a door's. `tests/e2e/labels.spec.ts` checks the card's half, at every frame drawn: the card shows exactly when the crosshair's target is an artwork, and a card clicked in the orbit view goes when walk mode begins and stays gone after it. `tests/e2e/routes.spec.ts` checks the two together on its walk of routes R1 and R5 (review 7, F30). The walk goes from the plaza through the entrance's middle doors (the prompt, the eye turned onto a leaf), on through the Great Hall and up the Grand Staircase to the Triumph of Marius (the card), and back out through the doors onto the plaza (the prompt again). At every frame drawn the card and the prompt never both show, each shows only with its own kind of look target, and there are frames with the prompt alone before and after the card and frames with the card alone.
  - `window.__met.label` is the artwork whose card the last frame showed: its id and title, or null.

## Budgets

The finished model: at most 3,000,000 triangles per frame counting instances, at most 900 instanced meshes, all geometry built in under 4 seconds on this machine. A unit test computes the first two from the sequence without WebGL. The e2e suite bounds the third from above: from navigation start to `window.__shotReady` on the dev server, which also covers loading the modules (and any geometry they build on import), starting the renderer and the first frames, must take under 4 s. Walk mode at `t = N`: the collision built in at most 2 s, and a walking frame's median work and mean GPU-synced render under 16.7 ms and its median frame interval under 18.37 ms (16.7 ms plus 10%), both on this machine (`tests/e2e/walk.spec.ts`, `tests/e2e/routes.spec.ts`). Of the first two, the collection's placeholders take at most 110 meshes and 600,000 triangles (`src/model/collection/placement.test.ts`).

The doors take at most 20 meshes and draws, their timeline meshes, the door layer's stand-ins and its doorways' one mesh together (17; `src/model/doors.test.ts`); with the look target on, the slowest frame of a door's swing takes under 16.7 ms of work facing into the Great Hall from the landing, opening and closing, and in the hall facing out, closing and opening, and the slowest walking frame through two full cycles walked to and fro before the door facing into the hall, the leaves' collision following them (M2b), and a GPU-synced render facing into the hall through the open doorway under 16.7 ms (`tests/e2e/doors.spec.ts`).
