# The Met — design spec

The contract every part of this repo builds against. Change it here first, in the same commit as the code that needs the change.

## Product

One page, `index.html`. It shows a procedural model of The Metropolitan Museum of Art's main building on Fifth Avenue, New York, in its present-day form, outside and inside. The model is never simply loaded: it is assembled by an ordered list of build steps, and the viewer plays that build forward or backward, one step at a time or continuously, scrubs it, jumps between chapters, and orbits, zooms and moves freely at any point. The page opens on the finished building, the last frame of the build; Play runs the build from the empty site. A walk mode puts the viewer on the ground in first person, to walk through what is built at the current position.

The order of the build is the order the real building grew: chapters are historical eras (the 1880 Vaux building, the 1902 Hunt facade and Great Hall, the McKim, Mead & White wings, the Roche-Dinkeloo additions, the 2014 plaza). Within a chapter, steps follow the order a builder would raise it: ground and footprint, structure and walls, openings and ornament, interior, roof. Only parts that exist today are modelled; each appears in the era it was built. The research behind the chapter list is in `docs/research/`.

Interior spaces are reached in three ways: interior camera presets, a horizontal section cut that removes everything above a chosen height, and a floor picker that shows one floor at a time with everything over it removed. Ten of them hold placeholders of real objects on view there, sized and coloured from The Met's CC0 collection data (Collection).

## World frame

- 1 unit = 1 metre. +Y is up. +X is Manhattan north (up Fifth Avenue). +Z is Manhattan east (toward Fifth Avenue, so the main facade faces +Z). Right-handed.
- The Manhattan grid is rotated about 29° clockwise from true north. Only the sun direction uses true compass bearings; everything else is in grid axes.
- Origin: Fifth Avenue sidewalk grade, on the axis of the central entrance (the Great Hall's east-west axis), in the plane of the Hunt facade's main wall face behind the column screen.
- The block polygons in `docs/research/exterior.md` section 2 are the walls' outer faces (the OSM outline). On a line two blocks share, the older block builds the wall, inside its own polygon, and the newer builds none there. On the building's outer outline, mouldings (cornices, string courses, sills, copings and their modillions) may project up to 1.5 m beyond the line; walls and glass never do (coordinator, 2026-10-11).
- The decoded floor map (ignored, under `research/cache/`) and every plan position in `docs/research/interior.md` sit 3.1 m +Z of this frame; subtract 3.1 m from their Z (correction of 2026-10-11, recorded in `interior.md`).
- Named levels, extents and key dimensions live in `src/model/frame.ts`, one constant per fact, each with a comment naming its source in `docs/research/`. Builders read them from there and never restate a number another builder depends on.

## Build-step API

Area modules (`src/model/site/`, `core/`, `hunt/`, `mmw/`, `roche-north/`, `roche-south/`) export named step arrays; `src/build/sequence.ts` composes each chapter of `src/build/chapters.ts`, in that order, from those arrays (its `COMPOSITION` table), so a modeller adds steps without touching it. A step's `chapter` must name the chapter its array is composed into (a test checks it); a chapter may have no steps yet. Every step array an area module's `index.ts` exports must be composed (a test checks it). Step ids are unique, stable and kebab-case, because URLs and tests name them. The types live in `src/build/types.ts`.

A step's `year`, when set, lies inside its chapter's `years` (a test checks it; `before 1872` means up to 1872). So Roche's 1970 information desk in the Great Hall is built in `roche-steps-lehman-1975`, and `mckim-mead-white-1926` runs 1904–1956 to hold its two 1956 steps.

```ts
interface StepDef {
  id: string;              // unique, stable, kebab-case
  chapter: ChapterId;      // from src/build/chapters.ts
  title: string;           // at most 48 characters, shown in the timeline
  detail?: string;         // at most 200 characters, shown under the title
  year?: string;           // overrides the chapter's years in the label, e.g. '1975'
  motion: Motion;          // how this step's pieces arrive
  stagger?: Stagger;       // the order pieces arrive in within the step; default 'order'
  weight?: number;         // playback duration multiplier; default 1
  focus?: CameraFocus;     // what the follow camera frames during this step
  build(kit: Kit): void;   // adds this step's pieces
}

interface Kit {
  // One piece: a shared geometry, a shared material and its final world matrix.
  add(geometry: BufferGeometry, material: Material, matrix: Matrix4, order?: number): void;
  // One piece of a door or an artwork: as add, and the timeline keeps its tag (Piece tags below).
  addTagged(geometry: BufferGeometry, material: Material, matrix: Matrix4, tag: PieceTag, order?: number): void;
  // A light that switches on with the step; at most 8 in the whole sequence, never shadow-casting.
  light(light: PointLight | SpotLight): void;
}

interface PieceTag { kind: 'door' | 'artwork'; id: string } // id stable and unique within its kind: a door's own id, an artwork's Met object ID

interface Chapter { id: string; title: string; years: string; summary: string } // src/build/chapters.ts

type CameraFocus =                                         // default { kind: 'pieces' }
  | { kind: 'pieces' }                                     // this step's piece bounds, from the current viewing direction
  | { kind: 'box'; min: Vec3; max: Vec3 }                  // this world box, from the current viewing direction
  | { kind: 'view'; position: Vec3; target: Vec3 }         // this exact camera
  | { kind: 'preset'; id: string };                        // a preset of src/viewer/presets.ts

type Motion =
  | { kind: 'rise'; distance?: number }                    // slides up from below its final place
  | { kind: 'drop'; distance?: number }                    // slides down from above
  | { kind: 'grow' }                                       // scales up in Y from its own base
  | { kind: 'pop' }                                        // scales up from its own centre
  | { kind: 'slide'; from: readonly [number, number, number] }; // arrives from this world offset

type Stagger = 'order' | 'x' | '-x' | 'z' | '-z' | 'y' | 'radial' | 'none';

type Vec3 = readonly [number, number, number];
```

- **Batching.** Within one step, pieces that share the same geometry object and the same material object become one `InstancedMesh`. Steps never share a mesh, so each step shows and hides independently. Builders therefore create one geometry per distinct shape and reuse it, and take materials from the shared palette (`src/model/palette.ts`) or their own module, never cloning a material per piece.
- **Piece tags** (contract C1 of work unit 2). `addTagged` adds a piece of a door or an artwork. The timeline keeps each tag with the instance the piece lands in: `Timeline.tagOf(mesh, instance)` gives it (null for an untagged piece), and `BuiltStep.tags` lists them per mesh. A door's pieces batch only with pieces of the same door, so each door has meshes of its own and can be shown or hidden on its own; an artwork's pieces batch as untagged pieces do. Tags are not timeline state: they never change with `t`, and every piece's matrices, colours and arrival are what `add` would give it. A tag of another kind or without an id fails, naming the step and the piece (`src/build/tags.test.ts`).
- **Composite pieces.** A part made of several materials (a window: frame and glass) is several `add` calls with the same `order`; pieces with equal stagger keys arrive together, and a test checks that every role of a window or door part arrives with the others. Spatial staggers key on the piece's world bounding-box centre, rounded to 1 cm; `radial` keys on the horizontal distance from the centre of the step's bounds; `order` defaults to the call's index within the step.
- **Motion details.** `rise` and `drop` travel `distance` metres, by default the piece's own height but at least 3 m; `grow` scales world Y about the bottom of the piece's world box; `pop` scales about its centre with a slight overshoot. Windows are paced by rank: of R distinct keys, rank r starts at `r / (R − 1) × (1 − d)` and lasts `d = max(0.25, 1 / R)`.
- **Materials.** A material with `userData.castShadow === false`, or any transparent one, never casts shadows (glass, water, the flat ground materials of the palette and the bronze of the entrance doors' leaves, Page, Doors). A material with `userData.solid === false` is walked through: the walk mode's collision leaves its pieces out (water, foliage, the jets of the plaza fountains, and the passable copies of the bronze and dark glass of the central doors' frames and leaves, not yet solid; Page, Doors); every other material is solid. The engine gives every model material the section-cut clipping plane, except one with `userData.sectionCut === false`: the cut leaves it whole and its cap pass leaves its meshes out. Everything the site builds as landscape opts out (trees, ground, streets, paths, rocks, walls, fences, lamps, benches, fountains and the plaza's furniture), using the site's own copies of materials the building shares, so only the building is cut; the excavation, the pad and the 1970 front steps are the building's and stay cut. A floor view hides the landscape that rises above its cut whole instead (Page, Floor picker). Builders never set `clippingPlanes`.
- **Lights.** A step light's intensity follows its step's progress (0 at `f = 0`, its own intensity at `f = 1`); lights never toggle visibility, so shaders never recompile during playback.
- **Timeline position.** With N steps, the position `t` runs over `[0, N]`. Step `i` (0-based) has local progress `f = clamp(t − i, 0, 1)`. At `f = 0` none of its pieces is visible; at `f = 1` every piece sits exactly at its final matrix; in between, each piece moves through its own window of `f` according to `motion` and `stagger`, and an arriving piece is briefly tinted so the eye finds it. An integer `t = k` is a rest position: steps 1..k (1-based) are complete and nothing is moving.
- **Determinism.** The scene state at `t` is a pure function of `t`. Evaluating `t` after any history of plays, reversals, steps and scrubs gives byte-identical instance matrices, colours and visibilities to evaluating it fresh. Caching may skip rewriting unchanged values; it may never make the result depend on the path. This is what makes backward playback exact, and a test asserts it.
- **Playback.** Play forward and play backward run `t` continuously at `weight × BASE_SECONDS / speed` seconds per step and stop at 0 or N. Step forward animates to the next integer, step back to the previous one; a second press while moving retargets. Scrubbing sets `t` directly. Speed is 0.5×, 1×, 2× or 4×. Play forward at N starts again from 0, and play backward at 0 from N. The player is pure logic with no DOM and is unit-tested on its own.

## Page

- **Timeline bar** (bottom): buttons for start, step back, play backward, play/pause, step forward, end; a speed control; the Walk toggle (`walk-toggle`, pressed in walk mode); a scrubber over `[0, N]` with chapter boundaries marked; a label `Step k / N · <year> · <chapter> — <title>` with the step's detail beneath, where k = ⌈t⌉ (the step just completed at a rest position, the step playing in between) and k = 0 reads `— Empty site`. Every control has an accessible name and a `data-testid`. While walking the bar folds into a strip at the bottom right holding the Timeline button (`bar-toggle`, "Show the timeline", with `aria-expanded`) and the Walk toggle; the Timeline button unfolds the whole bar, whose controls then work as in the orbit view, and folds it again; each entry into walk mode starts folded. In the orbit view the bar is always whole and the Timeline button is hidden.
- **Chapter menu**: the chapters in order, with their years and summary; choosing one moves to the start of its first step; a chapter with no steps is shown disabled.
- **View menu**: exterior and interior camera presets (named in `src/viewer/presets.ts`: `fit` presets frame the model's bounds from a direction; `look` presets are explicit cameras with an optional `fov` and, for straight-down views, `up`), a follow-camera toggle that frames each step's `focus` during playback and switches off when the user drags, zooms or moves the camera by keys (a press without movement leaves it on), one button per walk spawn (`walk-spawn-<id>`, "Walk from ...", which enters walk mode there), and a section cut (an on/off toggle and a height slider). The cut keeps `y < cut` for every building material, shadows included (landscape opts out; see Materials), and draws the back faces of cut solids in one flat colour so cut walls read as solid from above. That pass draws only the pieces the cut passes through, by their current bounds (`src/viewer/cap-pass.ts`), so a piece under the cut never shows the cut colour, and it is drawn 4 depth-buffer steps nearer (`CAP_DEPTH_BIAS`, `src/viewer/section-cut.ts`), so a cut solid's face that lies on another piece's face (a stair's underside on its floor, a flight's end on its landing) shows the cut colour instead of z-fighting with it.
- **Floor picker** (`floor-picker`, a group named "Floor"): a column of buttons at the left of the view, All (`floor-all`) at the top and the floors under it from the highest down (`floor-<id>`), the choice in view pressed; Page Up and Page Down move up and down it. The floors are data in `src/viewer/floors.ts`, each with its id, label, level (from `src/model/frame.ts`), the section-cut height that shows it and the plan area the camera frames, picked by looking at the model:
  - `ground` (`GROUND_FLOOR_Y`), cut at 3.1 m: under the Temple of Dendur pool's slab (underside 3.41 m), the lowest slab over the ground floor.
  - `main` (`MAIN_FLOOR_Y`), cut at 7.8 m: under the Wallace Wing's mezzanine (underside 7.91 m), the lowest slab over the main floor, so no mezzanine (8.4 to 10.0 m) covers it.
  - `second` (`SECOND_FLOOR_Y`), cut at 12.7 m: over the Roche wings' second floor (12.34 m) and under the Fifth Avenue links' second-floor slab (13.15 m); every cut from 13.15 to 15.0 m slices a slab or roof, and one at 15.2 m leaves the Morgan wing's roof over its second floor.
  - `roof-garden` (`ROOF_GARDEN_Y`), cut at 27.4 m and framing the garden alone: over its potted trees (26.9 m) and the park's tallest crown (27.3 m); nothing stands over it.
  - Choosing a floor sets the cut to the floor's height, hides the landscape that rises above it, and frames the floor's storey from above at 65°, from the side the camera looked from (the orbit's horizontal direction is kept), turning the follow camera off as a preset does; the framing is fitted again after a resize while the camera stands there. Choosing it again frames it again.
  - Hidden landscape (`src/viewer/floor-view.ts`): every landscape mesh whose highest standing piece rises above the cut, whole, never sliced; a landscape piece at least 30 m across both ways is ground (the terrain, the merged park paths) and never hides, and pieces of one step with the same final matrix (a tree's trunk and crown, a lamp's post and globe) hide together. Hidden meshes neither draw nor cast shadows, and the zoom's pick passes through them.
  - All gives back the cut the user had before the first floor was chosen, on or off at its height, shows every landscape piece again and leaves the camera where it is. Moving the cut slider or pressing the cut toggle ends the floor view instead (All is pressed again) and the hand-set cut stands as the user's own.
  - Walk mode belongs to the walker: entering it ends the floor view as All does, the picker hides while walking and the floor keys do nothing. The walk's collision never reads the floor view, so it is the same whether a floor was chosen or not.
  - Like the cut, the floor view is a view filter: it sets the cut and each hidden mesh's layer mask, never what the timeline writes, and which meshes hide depends on the floor alone, read from each piece's final matrix, so the scene at `t` stays a pure function of `t` (and the floor).
  - Known limits: the map's floor-3 plates (the north end pavilion's at 15.9 m, the 1924 American Wing's at 13.9 m) have no entry, because no single cut shows them without slicing roofs elsewhere; the mezzanines (map floor 1M) have none, and the main floor's cut passes under them; where a wing's second floor lies higher than the frame's level (the Fifth Avenue links' at 13.6 m, the American Wing's at 14.1 m), the second floor's cut shows that wing's floor below. Landscape hides by whole meshes, so one standing piece over the cut hides every piece of its mesh, and an object placed with different matrices (the magnolias by the steps) can lose its crown alone.
- **Camera framing**: presets and the follow camera frame the part of the canvas above the timeline bar; walking, the view is the whole canvas (Walk mode: The screen). A preset lands exactly where it says, even right after a drag. When the canvas changes shape, the preset in view is fitted again, as long as the camera still stands where the preset put it. The neutral workspace ground, not part of the model, lies 0.5 m below the lower of grade and the model's lowest point, so model terrain always lies on top of it.
- **Follow camera at load**: on unless the query sets `shot=1`, a `view=` that names a preset, `cam=`, `walk=1` or a `floor=` that names a floor. It moves the camera only while the build plays.
- **No WebGL 2**: if the renderer cannot start, the page says WebGL 2 is not available, gives the browser's reason and what to do, and does not report a build failure.
- **Camera** (orbit view): drag to orbit, right-drag to pan, and the wheel, a pinch or a middle-button drag to zoom toward the pointer (`src/viewer/zoom.ts`). A zoom step moves the camera along the ray under the pointer and keeps its view direction. In, it moves a tenth of the distance to the surface under the pointer (`src/viewer/pick.ts`: the first drawn piece, or the workspace ground; above the section cut, cut pieces are passed through, and so is the landscape a floor view hides), at least 0.25 m, and stops 0.5 m before that surface, or sooner on the ray where the ray comes down to the camera floor (0.4 m above the workspace ground), which it then heads for instead; over open sky it flies on as if a surface stood 10 m ahead. Out, it moves a tenth of the distance to the orbit target, at least 0.25 m, until the target is 6 km away, or, backing down a ray that points up, until the camera stands on the camera floor, still on the ray. Where the camera is at both bounds at once (zoomed out to 6 km, then lowered onto the floor by Q), a notch out first brings the target onto the view axis at the near bound's depth and then moves (`zoomStep`). Each step puts the orbit target on the view axis at the depth of what it heads for. Steps never shrink toward an invisible point, so every notch moves the camera until one of the two bounds, and either bound gives way at once to the other direction (`docs/learning/defect-register.md`, "The wheel stops zooming"). The camera stays 0.4 m above the workspace ground: a pan or an orbit that takes it lower is undone by lifting the camera and its target together, so the view does not turn. That lift is the last move before each frame renders, so no frame renders from under the floor; what the drag still owes carries the camera on over the next frames, each lifted again. A zoom first spends what a drag still owes and makes that lift, then takes its ray.
- **Keyboard**, by physical key (`event.code`), in two modes. A key takes the meaning of the mode in force when it is pressed, so a key pressed right after F, before the next frame, already belongs to the new mode. A focused button keeps Space and Enter, a focused slider other than the scrubber keeps its arrows, Home, End, Page Up and Page Down, and a text field keeps every key.

  | Key | Orbit view | Walk mode |
  |---|---|---|
  | Space | play/pause | jump |
  | Shift+Space | play backward, or pause | jump |
  | → / ← | step forward / step back | walk right / left |
  | ↑ / ↓ | nothing | walk forward / back |
  | Home / End | go to start / end | nothing |
  | Page Up / Page Down | up / down a floor of the floor picker, All above the top floor, staying put at either end | nothing |
  | W / S | move the camera and its target forward / back along the view laid flat | walk forward / back |
  | A / D | move them left / right | walk left / right |
  | Q | move them down | nothing |
  | E | move them up | opens or closes the door looked at (Doors) |
  | Shift, held | doubles the speed of W A S D Q E | runs |
  | F | enters walk mode | returns to the orbit view |

  Orbit-view moves run at half the camera-to-target distance per second, at least 1.5 m/s (`src/viewer/orbit-keys.ts`), so they cover the same share of the view from an aerial preset as from inside a hall. They keep the camera above its floor and turn the follow camera off, as a drag does.
- **Walk mode** (`src/walk/`), entered by the Walk toggle, F, a view-menu spawn or `walk=1`:
  - **Body.** A capsule of radius 0.35 m and height 1.75 m, the eye 1.6 m above its feet. It walks at 2 m/s and runs at 5 m/s, jumps 0.45 m and falls under gravity (9.81 m/s²). The walk is a brisk walk indoors, about 1.4 times a person's comfortable 1.4 m/s, because motion seen on a screen looks slower than the same walk in life; 3 m/s read as a jog (work unit 2 audit). The run is 2.5 times the walk, to cross the 300 m building in about a minute; 6 m/s was a sprint.
  - **Ground.** It steps up and down edges of up to 0.35 m, so stairs and the front steps are climbed by walking. It steps up only where its raised body meets nothing overhead: under a ceiling, soffit or lintel too low for it, a step stops it like a wall, so its head never enters what is over it. It walks on slopes up to 40°; a steeper one stops it like a wall, and it slides down one it lands on, the keys unable to push it uphill. It stands on the surface under its centre or, over a gap, on the lower rim of two opposite probes 0.3 m out, so it bridges a gap narrower than about 0.6 m yet falls off an edge as soon as its centre passes it. It slides along walls. Physics runs in fixed steps of 1/120 s, so a walk is the same at any frame rate. The eye eases out of each snap up or down a stair over about 0.1 s, and each frame's eye is interpolated between the eased eyes of the last two steps, so on a flight it never drops while climbing and never rises while descending, no frame moves it more than the climb covers in that frame plus half a riser, and it stays within 0.3 m of 1.6 m over the feet (`src/walk/stairs.test.ts`, `tests/e2e/stairs.spec.ts`).
  - **Looking.** A click on the view asks for pointer lock, and the mouse then turns the view; Esc frees the pointer, as browsers do. A drag with the mouse or a finger turns the view too, locked or not. Pitch stays within ±85°; the field of view is 60°. Choices (work unit 2, M1), each in `src/walk/walk-mode.ts`:
    - A drag turns the view the way the pointer moves, right for right and up for up, as the locked mouse does, so one hand motion means one thing in walk mode whether the pointer is locked or not, as in first-person games on a desk or a phone. The orbit drag turns the other way because it turns the model about a target in the hand, not the head.
    - `LOOK_PER_PIXEL` 0.0013 rad (0.075°) a pixel, locked or dragging: a drag across the view turns it by about its own width (91.5° over 1280 px at 1280×720, 29.8° over 390 px at 390×844), precise enough to look round a gallery; 0.0022 turned 1.8 times that.
    - `CLICK_SLOP` 5 px: a press that travels less before it is released is a click, which asks for pointer lock; more is a drag, which looks. A still click travels 0 to 2 px, and under 5 px a drag would have turned the view by under 0.4°, which nobody means as a look.
  - **The screen.** While walking: the view, now the whole canvas (the projection is centred on it whether the bar is folded or not, so unfolding it never moves the view); a crosshair (`crosshair`) at its centre, on the eye's ray, gold while the look target is a door or an artwork; the Chapters and View buttons at the top right; and the folded bar's Timeline button and Walk toggle at the bottom right. The rest of the bar and the floor picker are hidden. The status line (`walk-status`) says "Preparing walk mode…" for the first frame, then how to look, move and leave until the visitor first walks or looks, at most `HINT_SECONDS` (6 s), and again when the pointer is freed; while the pointer is locked the browser says how to free it. Hidden controls come back by the Timeline button. Walk mode ends by F, the Walk toggle, or a camera preset from the View menu.
  - **Look target** (contract C2 of work unit 2; `src/walk/look.ts`), the only way doors and labels find what the visitor looks at. The hit query (`ModelPicker.hit`, `src/viewer/pick.ts`) casts a ray through the drawn pieces as the zoom's pick does and returns the nearest piece a query accepts, with its mesh, instance, distance and tag; a surface the query does not accept stops the ray, except that a query may pass through untagged transparent pieces (glass, water), so an artwork in a vitrine is found through its glass but never through a wall; a tagged piece the query does not accept stops the ray as a wall does, so a glass door out of reach hides what is behind it (accepting a target and passing through are apart; the zoom's own `distance` still stops at glass). The walking eye asks for the nearest tagged piece within its kind's reach, a door within 2 m and an artwork within 6 m, through transparent pieces. Walk mode runs it every walking frame and again whenever the target is read (`WalkMode.target()`, `window.__met.walk.target`), so an action sees the view as it stands then; the same query serves a pointer ray from an orbit-view click. Viewer-side stand-ins, a door's moving leaves for one, join the picker with their own tags through `ModelPicker.register(meshes, tagOf)` and leave through `unregister(meshes)`: both queries meet them as drawn pieces (visible, on a layer the camera draws, their first `count` instances at instance matrices in world space, the mesh itself untransformed, its bounding sphere trusted as the renderer's culling trusts it, so a stand-in that moves keeps it current), their BVHs are built in the shared cache as they join, and an original moved onto a layer the camera does not draw drops out. `WalkMode.onLookTarget(listener)`, which returns the call that stops it, is the one hook that hears the target: it calls the listener with the target, or null, each time its kind or id changes as walking frames find it (not when only its distance changes, and not on a fresh read, which the next frame tells), and with null when walk mode is left or entered again while a target was seen. Doors and labels both subscribe there; neither adds a hook of its own, nor door or label logic to the picker or walk mode.
  - **Collision.** Every piece of every step complete at the current `t` (f = 1) whose material is solid, at its final matrix, through a three-mesh-bvh BVH per distinct geometry and a grid over the instances. Neither the section cut nor the floor view changes it. It is built on entering walk mode, after one frame showing "Preparing walk mode", and again whenever the set of complete steps changes while walking.
  - **When the build moves.** Where nothing is built under it, at t = 0 for one, the walker stands on the workspace ground; a spawn over nothing puts it there at once, without a fall. Each time the collision is built, while walking or on entering, the walker's place is checked against it (`settle`, `src/walk/walker.ts`). It is buried when the model lies over it with nothing but the workspace ground under it, and embedded when the vertical line through it, from just over its feet to its head, runs inside a piece that arrived since its place was last checked. Along that line a piece's inside lies between its first and second crossings, its third and fourth, and so on; a piece the line crosses an odd number of times is open there and has no inside. A buried or embedded walker moves at once, at rest, to the lowest walkable surface over its feet where it stands clear: no surface crosses the line from 0.35 m over that surface to its head, no piece's inside reaches that span, and nothing overhead meets its raised body. With no such surface it goes to the nearest spawn. A walker that stands clear stays where it is, and one whose ground is taken away falls, as off an edge. So End from t = 0 puts it on the plaza, Home drops it to the workspace ground, and the build played while walking lifts it out of each step that completes over or through it.
  - **Entering and leaving.** Entering puts the walker at the spawn asked for, else where it last stood in this page, else at `plaza`. While walking, the timeline keys are off, the bar's controls still work once it is unfolded, the follow camera is off, and the status line says how to look, move and leave (The screen). Choosing a camera preset in the view menu leaves walk mode first and then lands on the preset, which is then the preset in view. Leaving puts the orbit camera at the walker's eye with its target 5 m ahead, at the field of view it had before. Walking reads the scene and never writes it.
  - **Spawns** (`src/walk/spawns.ts`): `plaza`, on the entrance axis halfway between the foot of the front steps and the curb, facing the facade (the default); `great-hall`, on the Great Hall floor 8 m in from its north end, facing south down the nave; `second-floor`, on the landing at the top of the Grand Staircase, facing down it.
  - **No trap, no dead end** (work unit 2, M1; each checked against the building in `docs/research/interior.md` first). The Temple of Dendur pool's bottom lies 0.3 m under the walkways, inside the walker's 0.35 m step, so a walker who steps in climbs out over the square edge on either walkway side. The gate on the temple's axis is walked into from the forecourt, as visitors do, and not crossed from the terrace: its passage is filled with granite to the forecourt's level, and its front is a 0.79 m riser behind a 0.45 m steel rail on the terrace, an edge the walker sees rather than an invisible wall. The cross hall at the top of the Grand Staircase opens on its axis into gallery 600 through a round-arched doorway 3.5 m wide, its passage lined in stone through both walls (route R5, `src/model/hunt/routes.ts`).
- **Doors** (work unit 2, M2a; `src/model/doors.ts`, `src/viewer/doors.ts`). A door is one doorway's leaves, the pair or the one leaf of the parts library's `doorUnit`, with a stable id. The doors that open are the three doorways of the Hunt central arch, the Fifth Avenue entrance (`hunt-entrance-south`, `hunt-entrance-middle`, `hunt-entrance-north`). Locked, whatever is asked of them: the McKim, Mead & White links' doors (`mmw-north-link`, `mmw-south-link`) and the Branch Bank's door in the Engelhard Court (`bank`), each over a drop behind it (2.9 m and 0.65 m). Weston's 1888 door into the Petrie Court stays a closed, solid piece with no tag until M2b makes it a door together with its collision. Gallery doorways are open portals with no leaves.
  - **Pieces.** A build places a door's leaves closed (`DoorParts.leaf`, and `leafGlass` for a glazed door) through `kit.addTagged` with the door's tag (`doorTag`), so each door has meshes of its own (Piece tags); its frame and fanlight are untagged. An id names a doorway, so a pair's leaves open together: the entrance's doorways are 1.8 m wide, and one 0.8 m leaf would leave less room than the walker's 0.7 m body needs once the collision follows the leaves. Each of the entrance's doorways is, after S8 (Haklai 2012) at full size, a bronze frame holding a pair of glazed leaves, one tall pane each in a bronze frame 9 cm wide, up to a transom bar at 54% of the opening (2.6 m of 4.79 m), and a fixed transom light over it, in the bronze and dark glass of the fixed glazing they replace (`docs/research/exterior.md` H11 and C4).
  - **Hinges.** Each leaf hangs 4 mm clear of its frame, its sill, the transom bar's underside and the other leaf of its pair, and turns about its hinge-side edge at the face it opens round: about its back face's edge opening toward the back, about its front face's toward the front. So swung either way it meets no fixed part of its unit (a check every 2.5° through the whole swing, `src/model/lib/door.test.ts`), and a quarter turn open it stands 4 mm off its jamb. A pivot in the leaf's mid-plane swept the hinge edge's corner about 12 mm into the jamb mid-swing, and leaves up to the bar's centre line passed 41 mm into it (review 5, F22). It opens a quarter turn (90°) either way, as a double-acting door does, so it can always swing away from whoever opens it.
  - **The layer.** Once the door's step is complete (f = 1), the door layer hides the timeline's closed leaves by their layer mask, a presentation filter like the floor view's that never writes their matrices, colours, counts or visibility, and draws each leaf in a stand-in mesh at the closed piece's final matrix times its turn about its hinge. A stand-in holds one leaf's geometry with the closed piece's material, so the section cut clips it alike; its bounds cover every pose of its leaves, for culling and the cap pass; it casts a shadow only if the leaf does; and it is registered with the zoom's pick, the hit query and the cap pass, so each meets the leaf where it stands. The page draws again at each swap and on every frame of a swing, and redraws the shadows only when what moved casts one. A locked door has no stand-in and is never hidden.
  - **No shadow from the entrance's leaves** (review 5, F23). The leaves' bronze (`hunt.doorLeafBronze`) casts no shadow, and their glass, like all glass, none, so a swing's frames redraw no shadows. The reason is the frame's cost: facing into the Great Hall from the landing, a swing's frame takes 655 draw calls instead of 1,285 with a shadow pass, and its slowest frame 5.7 ms of work instead of 10.9 ms (a probe at 60 Hz, 2026-10-27). What it costs to look at, the same views captured with the leaves casting and not: closed, no pixel differs by more than 6 of 255 in a channel; open, the leaves' faint shadow just inside the doorway, on the floor and the first piers' bases, is missing, at most 19 of 255, on 549 pixels of the entrance seen from the plaza (0.06% of 1280×720) and 4,046 of a view from the doorway into the hall (0.44%) differing by more than 8.
  - **Lifecycle.** While the door's step is incomplete (f < 1) the timeline's closed leaf takes over at once and the door cannot be used; the door keeps its state, which it shows again at once when the step completes. When the timeline takes the step away (f = 0) its state resets, so the first completion, and each one after the step was taken away, gives the door its default: closed, or open with `doors=open`. With no walker to open it away from (at load), a door opens into the building, toward its back.
  - **Use.** Walking, a door the look target meets within 2 m shows "E Open", "E Close" or "Locked" under the crosshair (`door-prompt`), inside the band x = centre ± 160 px, y = centre − 8 px to centre + 80 px, which M3b's label card keeps out of; the prompt follows the look target through walk mode's one hook (`WalkMode.onLookTarget`) and the door's state each frame. E, or a click while the pointer is locked, reads the look target afresh (`WalkMode.target()`) and swings the door it meets away from the walker, a full quarter turn in 0.7 s, eased (smoothstep), so the swing starts and ends at rest; used again mid-swing it turns back from where it stands. An open door's leaves stand against their jambs, so it is closed by looking at a leaf there. A locked door never opens, by any input or query, and `doors=open` leaves it shut. In the orbit view E keeps its meaning. Walk mode moves by keys only, so on a phone it shows the prompt but cannot use a door (plan, Amendments after M1).
  - **Walking.** In M2a the leaves of the doors that open are not yet solid: like the fixed glazing they replace, their bronze and glass are passable copies of the palette's, so every route walks as before; the collision follows the leaves in M2b. The locked doors' leaves are solid, as before, and stop a walker against them (`src/model/doors.test.ts`).
  - **Budget.** The doors take at most 20 meshes and draws, the layer's stand-ins counted (`src/model/doors.test.ts`).
  - **Facts.** `window.__met.doors` lists every door the timeline holds, in step order: its id, `state` (`closed`, `opening`, `open` or `closing`), `angle` (degrees open, positive toward its back), `locked`, and `built` (its step complete; while it is not, the state and angle are what the door shows again when it is), as a detached, frozen snapshot like every fact (`DoorFacts`, `src/viewer/doors.ts`). The page marks its door set-up at load (performance mark `met:doors-set`) and, with `walk=1` and `shot=1`, the walker's placement after it (`met:walk-placed`), so a test reads their order beside the first drawn frame (`tests/e2e/doors.spec.ts`).
- **First load**: the page opens on the finished building, `t = N`, paused, in the orbit view at the default preset. `autoplay=1` plays the build on load instead, from `t = 0` unless the query sets a position. Play at `N` starts again from 0, as Playback says.

## Query contract

`src/viewer/query.ts` is the only reader of the page URL.

| Parameter | Effect |
|---|---|
| `shot=1` | Capture mode: no autoplay, no follow camera, no animation; `window.__shotReady = true` once at least 5 frames have rendered at the requested state |
| `t=<number>` | Timeline position in `[0, N]` |
| `step=<id or 1-based index>` | Position at the end of that step; wins over `t` |
| `view=<preset id>` | Camera preset; one that names no preset is ignored with a warning, as if absent |
| `cam=px,py,pz,tx,ty,tz` | Explicit camera position and target, for sweeps |
| `cut=<metres>` | Section-cut height |
| `solo=<chapter id>` | Build only that chapter (plus `site`), for fast isolated checks |
| `autoplay=1` or `autoplay=0` | `1`: play the build on load, from `t = 0` unless `t` or `step` sets a position. `0`: do not play, the default |
| `walk=1` | Start in walk mode |
| `spawn=<id>` | With `walk=1`, the walk spawn to start at (`plaza`, `great-hall`, `second-floor`); one that names no spawn starts at `plaza` with a warning; without `walk=1` it is ignored with a warning |
| `floor=<id>` | Start on that floor of the floor picker (`ground`, `main`, `second`, `roof-garden`; `all` shows every floor), framed unless `view=` or `cam=` names a camera; one that names no floor, or any with `walk=1`, is ignored with a warning |
| `doors=open` or `doors=closed` | The state every unlocked door takes when its step completes (Doors), at load and after the step was taken away; with `shot=1` the doors stand at it from the first frame, set before the walker is placed. Any other value is ignored with a warning; a locked door stays shut either way |
| `noui=1` | Hide the page chrome |

The renderer keeps `preserveDrawingBuffer: true`, or headless capture reads a blank canvas. `window.__met` exposes read-only facts for tests (step ids, titles, each step's `focus` and piece `bounds`, chapters with their first step and count, presets, bounds, `N`, current `t`, mode, speed, follow, the follow camera's current goal, cut, `floors` (each floor's id, label, name, level and cut), `floor` (the floor picker's choice in view, the landscape meshes it hides and the user's own cut it gives back), view, the camera with its `fov` and the `aspect` of the canvas above the bar, budget stats, `perf.buildMs` (the timeline build alone) / `perf.readyMs` (navigation start to ready) from `performance` marks, `perf.lastDrawn` (the last drawn frame's number and the camera position it was rendered from, copied right after the render), and `walk`: the mode (`orbit` or `walk`), whether it is preparing, the spawn last used and the spawn ids, the eye and the unit look direction (null in the orbit view), the on-ground flag, whether the pointer is locked, `bvhMs` (milliseconds of the last collision build), what that build holds (complete steps, instances, triangles) `frameMs` (the median work per walking frame over the last 120, the look target included) and `target` (the look target when read: the tagged piece's kind, id and distance, or null); types in `src/viewer/facts.ts` and `src/walk/walk-mode.ts`). In capture mode with `walk=1`, the collision is built and the walker placed before the first frame. Every value is a detached, deeply frozen snapshot, so no write to it reaches the page; tests drive the page through its real controls, never by writing state.

## Parts library

`src/model/lib/` exports pure functions that return `BufferGeometry` in local coordinates: origin at the part's base centre unless its header says otherwise, +Y up, the part's front facing +Z. Each function's header states its parameters' units and its origin. The set covers what the building repeats: classical column and pilaster (base, shaft, Corinthian capital), entablature and cornice profiles swept along a path, round-arched and flat openings in a wall, windows (frame, mullions, glass as separate geometries), balustrade runs, stairs, domes and saucer domes with or without an oculus, coffered vaults, skylights (ridge and pyramid), glass curtain walls, trees, fountains. Geometry is cached per parameter set so equal calls return the same object, which is what lets the kit instance it.

A door (`doorUnit`) returns its leaves closed, as one geometry for a build to place (with the leaves' glass as another for a glazed door), and each leaf apart, closed, in the unit's frame, with its hinge (the hinge-side edge's point on the leaf's back face and on its front face, and a unit axis turned so that a positive turn swings the leaf toward the unit's back, −Z; it turns about the back face's point opening toward the back and the front face's opening toward the front) and its swing (which way it may open and how far); `doorLeavesOf` finds the leaves from the closed geometry, for the door layer (Page, Doors).

## Collection

Placeholders of real objects on view (AGENTS.md non-goals; research, rules and regeneration in `docs/research/collection.md`):
- **Catalogue.** `src/model/collection/catalogue.ts` is generated by `scripts/met-catalogue.ts`, run by hand (`npm run met-catalogue`), never in CI or the build: from the picks (`src/model/collection/picks.ts`: 5 to 12 objects in each of at least 8 spaces), it fetches The Met's Collection API records at one request a second through an ignored cache (`research/cache/met-api/`), stops on HTTP 403 or 429 saying when to retry, rejects a record whose `GalleryNumber` is not its space's unless its pick overrides it, samples colours only from public-domain images (decoded in the system Chrome), and writes the file all at once or not at all. Each entry is one CC0 record: its metadata, the placeholder's derived kind, display, size and colours, where each came from, and its provenance (API URL, fetch date, hashes of the record and image, the sampler's version).
- **The page never fetches.** The catalogue is in the bundle; the page asks nothing of any host but its own and nothing of `research/` (`tests/e2e/network.spec.ts`). No image is a texture or committed.
- **Placeholders.** Each object takes a procedural form at its real size (`src/model/collection/kinds.ts`: a standing figure, a group, a recumbent figure, a bust, a jar or dish, a slab, a block, a canvas, each filling a unit box its piece's matrix scales): kinds figure, bust, vessel, slab, frame and plinth, shown on a plinth, in a vitrine (objects under 0.6 m), on a wall (paintings, and slabs from 0.6 m) or on the floor (`src/model/collection/place.ts`). Paintings show an 8 × 8 grid of their image's colours, blended bilinearly between cell centres (a soft blur, not a mosaic), everything else its sampled mean.
- **One step per space**, after that space's fit-out step, in its chapter and year, composed into an area module's array (`src/model/collection/spaces-a.ts`, `spaces-b.ts`). It pops its artworks in one after another (stagger `order`, one order per artwork, so an artwork's object and its plinth, vitrine or frame arrive together) and frames the space's preset.
- **Colour per instance without a mesh each.** A step's artworks share one material whose shader finds an instance's artwork by the plan position of its matrix in a float table (`src/model/collection/material.ts`): colour, roughness, metalness and a painting's grid. This holds because every form is centred in X and Z and the steps pop their pieces, which never moves them in plan, and because a step's artworks stand at least 5 cm apart in plan. The timeline's arrival tint still multiplies the colour; the determinism contract is untouched, the table being fixed per step.
- **Placement** (`src/model/collection/placement.test.ts`, at `t = N` against the model without the collection, reading each piece from the instance its step's mesh draws, bound exactly to the piece `kit.add` was given and to the one its placement gives): every artwork's pieces stand on the floor their placement names (within 12 mm) or hang against a wall (within 4 cm), no other solid passes through them, and they keep 1 m clear of routes R1–R5 (R5 into gallery 600) beyond the walker's radius, of the doorway into 600 with its passage's sides, of the Dendur gate's threshold and the rail before it, of the Dendur pool, of the Weston door's passage and of the swing of the doors that open (the Hunt central arch's and the Weston door).

## Budgets

The finished model: at most 3,000,000 triangles per frame counting instances, at most 900 instanced meshes, all geometry built in under 4 seconds on this machine. A unit test computes the first two from the sequence without WebGL. The e2e suite bounds the third from above: from navigation start to `window.__shotReady` on the dev server, which also covers loading the modules (and any geometry they build on import), starting the renderer and the first frames, must take under 4 s. Walk mode at `t = N`: the collision built in at most 2 s, and a walking frame's median work and mean GPU-synced render under 16.7 ms and its median frame interval under 18.37 ms (16.7 ms plus 10%), both on this machine (`tests/e2e/walk.spec.ts`, `tests/e2e/routes.spec.ts`). Of the first two, the collection's placeholders take at most 110 meshes and 600,000 triangles (`src/model/collection/placement.test.ts`).

The doors take at most 20 meshes and draws, their timeline meshes and the door layer's stand-ins together (`src/model/doors.test.ts`); with the look target on, the slowest frame of a door's swing takes under 16.7 ms of work facing into the Great Hall from the landing, opening and closing, and in the hall facing out, and a GPU-synced render facing into the hall through the open doorway under 16.7 ms (`tests/e2e/doors.spec.ts`).
