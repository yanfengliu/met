+# Mixed mouse and touch input never crashes the orbit view
+
+Status: active
+Owner: orbit, a worker of the met coordinator
+Created: 2026-10-29
+Updated: 2026-10-29
+
+## Problem and outcome
+
+Work unit 2's review 11 (F39, `docs/work/2_doors-and-collection/reviews/11_implementation.md`) reproduced a crash on the real camera rig: a mouse down and then a finger down threw `Cannot read properties of undefined (reading 'x')` inside three's OrbitControls (r186, `OrbitControls.js:1323`), and so did a finger down, a mouse down and the finger up (`:1639`), with the orbit view's click gate and without it. The owner gave the go on 2026-10-29. Outcome: mixed pointer input is arbitrated in met's code before OrbitControls and the zoom's input hear it, so no mix of mouse, pen and touch throws or moves the camera by a pointer that does not hold it, and every pointer passed on keeps its whole life, each press with its release or cancel.
+
+Cause: OrbitControls keeps a finger's position (`_pointerPositions`, for its two-finger pan) but not a mouse's or a pen's, and takes every pointer it hears for one of its own. With a mouse and a finger in its list, the finger's press, or the finger's release leaving the mouse alone in it, reads the mouse's missing position. The same holds for any two pointers of which one is a mouse or pen. While a pointer is down it also hears every pointer's moves and releases on the document, pressed on the canvas or not, so a pen's hover turned the view and a finger lifted elsewhere on the page threw.
+
+## Scope
+
+Included: the arbitration (`src/viewer/pointer-arbiter.ts`) and its wiring in the rig (`src/viewer/camera-rig.ts`) and the zoom's input (`src/viewer/zoom.ts`); the click gate's release while walking (`src/viewer/click.ts`), which the extended random sequences found; tests on the real rig for both orders of F39 and the rest of the class, the arbiter on its own, the seeded random sequences mixed (`src/viewer/click-random.test.ts`), and a Playwright check through the browser's own input; the spec's Camera and Labels sections and the Gates text in AGENTS.md.
+
+Excluded: walk mode's own input (`src/walk/walk-mode.ts`), which another session changes for mouse-look and Esc; three.js itself (node_modules is never patched); the wheel, which is no pointer.
+
+## Approach
+
+One kind of input holds the camera at a time: the fingers on the screen, any number, or one mouse or pen. A press on the canvas in the orbit view is passed on when nothing holds the camera, or when it is a finger and fingers hold it; every other press is refused, a pointer of another type, a second mouse or pen, and every press while walking. Each consumer, OrbitControls and the zoom's input, hears a passed pointer from its press to its end wherever its events land, and nothing of any other pointer, a refused one, one pressed elsewhere, or a hover. A passed pointer keeps its life through a change of mode, and a refused one stays refused to its end, even once the camera is free. The camera is free once every consumer has heard each holder's end, so no consumer ever holds two kinds of input, even one that missed an end.
+
+Mechanism: `PointerArbiter.consumer()` gives each consumer a filter its pointer listeners go through, with that consumer's own open pointers; a press is decided once, by the first consumer that hears it, so the listeners' order does not matter. The zoom's listeners go through its filter as `bindZoomInput` adds them. OrbitControls is built without an element, its three bound pointer listeners (`_onPointerDown`, `_onPointerMove`, `_onPointerUp`, which `connect` and its first press add, each read from the instance as it is added) are put through the filter, and then it connects to the canvas. These are private by convention, so the rig throws, naming the listener and what to change, where a release of three.js has none of them, rather than leave the controls hearing every pointer; the random sequences and the rig's table would turn red if a release kept the names but stopped using them.
+
+Tradeoffs: a pointer whose end a consumer never hears holds the camera until it presses again (Pointer Events 3 gives every press an end; the rig already relays a cancel landing elsewhere to the controls, review 11, F37). Rejected: stopping refused events in the document's capture phase, which would also hide them from the timeline bar's and the menus' listeners on the window; a proxy element for OrbitControls, more surface than three bound listeners.
+
+The click gate holds a sub-slop press's moves and dropped them at its release; released while walking, the press was no click, yet its held move was dropped all the same, so the consumers heard the release without the latest move (harmless while walking, since neither acts then, but a broken stream). It now sends the held move on there, as for any press that is no click.
+
+Why the random sequences missed F39: they were written around it. When review 11 deferred F39, the generator was built so that nothing pressed while a mouse or pen was down, no finger ended while one was, and no middle button pressed while a finger was down (its Bound said so), so that the rest of the class could be checked without the known crash. The throw check was there all along: with only those three rules lifted, 284 of its 400 seeds threw at `8a6a0c2`. It also never pressed on another element, never hovered and never changed mode, so the finger lifted elsewhere, the pen's hover and the walk-mode cases were out of its reach.
+

+/**
+ * Which pointers the orbit view's camera input hears (docs/design/spec.md, Camera; work unit 10). Its consumers are OrbitControls and the zoom's
+ * input (src/viewer/zoom.ts `bindZoomInput`). OrbitControls keeps a finger's position, for its two-finger pan, but not a mouse's or a pen's, and
+ * takes every pointer it hears for one of its own. So a mouse and a finger down together threw inside it (`Cannot read properties of undefined
+ * (reading 'x')`, work unit 2, review 11, F39), and so did a mouse and a pen, a middle button pressed while a finger turned the view, and a finger
+ * released elsewhere on the page while a mouse dragged; and a pen hovering while a mouse dragged turned the view by the pen.
+ * So one kind of input holds the camera at a time, the fingers on the screen, any number, or one mouse or pen:
+ * - a press on the canvas in the orbit view is passed on when nothing holds the camera, or when it is a finger and fingers hold it;
+ * - every other press is refused: a pointer of another type, a second mouse or pen, and every press while walking;
+ * - each consumer hears a passed press, then that pointer's moves and its end (its release or cancel) wherever they land, and nothing else: nothing of
+ *   a refused pointer, nor of a pointer pressed elsewhere, nor of a hover. A passed pointer keeps its whole life in every consumer, through a change of
+ *   mode; a refused one stays refused to its end, even once the camera is free;
+ * - the camera is free again once every consumer has heard the end of every pointer it was passed, so no consumer ever holds two kinds of input.
+ * Each press is decided once, by the first consumer that hears it, so every consumer hears the same presses whatever the order of their listeners.
+ * Bound: a pointer whose end a consumer never hears (Pointer Events 3 gives every press one) holds the camera until it presses again.
+ */
+
+/** A pointer listener as a consumer adds it. */
+export type PointerListener = (event: PointerEvent) => void;
+/** One consumer's filter: each of its pointer listeners put through it. */
+export type Hear = (listener: PointerListener) => PointerListener;
+
+export class PointerArbiter {
+  /** Each pointer a consumer holds, by its id: whether it is a finger. */
+  private readonly held = new Map<number, boolean>();
+  /** The pointers each consumer holds: passed to it, and not yet ended there. */
+  private readonly consumers: Set<number>[] = [];
+  /** Each press decided, by its event: whether it was passed. */
+  private readonly decided = new WeakMap<object, boolean>();
+
+  /** `active()` holds in the orbit view: a press while it does not is refused. */
+  constructor(private readonly active: () => boolean) {}
+
+  /** Whether the press `down` is passed on, decided by the first consumer that hears it. */
+  private passes(down: PointerEvent): boolean {
+    const known = this.decided.get(down);
+    if (known !== undefined) return known;
+    const finger = down.pointerType === 'touch';
+    const holders = [...this.held.values()];
+    // A pointer held and pressed again (its end was lost) goes on as it was.
+    const pass = this.held.has(down.pointerId) || (this.active() && (holders.length === 0 || (finger && holders.every((f) => f))));
+    this.decided.set(down, pass);
+    if (pass) this.held.set(down.pointerId, finger);
+    return pass;
+  }
+
+  /**
+   * A new consumer's filter: each of its pointer listeners, put through it, hears a passed press, then that pointer's moves and its end, and nothing
+   * else, so together they hear each passed pointer's whole life once.
+   */
+  consumer(): Hear {
+    const open = new Set<number>();
+    this.consumers.push(open);
+    return (listener) => (event) => {
+      const id = event.pointerId;
+      if (event.type === 'pointerdown') {
+        if (!this.passes(event)) return;
+        open.add(id);
+      } else if (!open.has(id)) {
+        return;
+      } else if (event.type === 'pointerup' || event.type === 'pointercancel') {
+        open.delete(id);
+        if (!this.consumers.some((o) => o.has(id))) this.held.delete(id);
+      }
+      listener(event);
+    };
+  }
+}
