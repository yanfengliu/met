- The build process is the product (owner, 2026-10-10): every visible part of the model arrives through a build step, and the page plays the steps forward and backward, one at a time or continuously. A part that exists only in the finished state is a defect.
- Fidelity is checked against photographs of the real building, outside and inside (owner, 2026-10-10). A modelling change names the reference images it was compared with, from `docs/research/`.
- The owner keeps a render gallery (owner, 2026-10-28): the private artifact https://claude.ai/artifact/YFUsoCGDEin8eGcUoxMPBV shows the standard shot set of main. After each merge to main that changes a render, take main's shots, rebuild the page with `python -I tmp/gallery/build.py <shots-log> "<note>"` and republish `tmp/gallery/index.html` to that artifact's URL. The builder lives under the ignored `tmp/gallery/`; on a fresh machine, rebuild it from the artifact's published page. While a coordinator session oversees the met sessions, it refreshes the gallery after each landing that changes a render; otherwise the landing session does, before it releases the landing slot.
- Landings on origin's main go one at a time (owner, 2026-10-28: "Make sure different threads don't step on each other"): take the slot with `bash /c/Users/38909/Documents/github/met/tmp/land.sh take <who>` (ignored; it exits 1 naming the holder when the slot is taken), merge origin/main into your branch, gate the merged tree (a merge that brings in docs only needs no gate), push the branch to origin's main, then `land.sh release <who>`. Merge origin/main, never the local `main`, and never commit onto the local `main`: every worktree of the clone reads it, and a session that builds on it carries what it finds there, as work unit 5's push carried work unit 2's unverified merge on 2026-10-28. On a fresh machine, recreate the script to that description.
- Expensive gates run one at a time across the met worktrees (fleet canon R5): run `npm run verify`, `npm run test:e2e`, `npm run shots` and `npm run sweep` through the main checkout's lock, `bash /c/Users/38909/Documents/github/met/tmp/gate.sh <who> <command...>` (ignored; set up by work unit 2), from the worktree under test. Waiters queue first come, first served, each with a ticket in `tmp/gate-queue` that goes stale 2 minutes after its waiter stops polling; the queue's head takes the lock, a `mkdir` of `tmp/gate-lock` holding its owner and start time, and releases only its own lock; a lock held over 30 minutes is broken, so keep each gated command under that and run longer sets as separate gated commands. On a fresh machine, recreate the script to that description. While its e2e runs, edit nothing the worktree's dev server serves: Vite reloads the open page, and a walk in progress fails (2026-10-28, `routes.spec.ts`: "Walk mode is not walking"). Stopping a background task that waits on the lock can leave `gate.sh`'s loop alive to take the lock later; end that loop's own process.
